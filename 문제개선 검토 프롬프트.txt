────────────────────────────────────────────────────────────────────────────────
Phase 1: 이슈 발굴
────────────────────────────────────────────────────────────────────────────────

대상 코드·기능을 읽고 잠재적 이슈를 발굴한다.

발굴 관점 (아래 순서로 검토):
  [버그]   예외 처리 누락, 경계값 오류, 경쟁 조건, None 미처리, 리소스 누수
  [설계]   책임 분리 위반, 순환 의존, 중복 로직, 잘못된 추상화
  [성능]   O(N²) 이상, 불필요한 API 반복 호출, 캐시 미활용, 블로킹 I/O
  [설정]   숫자 상수·파라미터 (→ 반드시 🔶사용자확인으로만 분류)
  [문서]   코드 동작과 주석·스펙 MD 불일치

발굴 시 필수 확인:
  각 잠재 이슈에 대해 D:\Main\Study\VSCode\DocChatRAG\스펙문서\00_카테고리_전체목록.md 를
  읽어 관련 스펙 MD를 특정하고, 이 패턴이 의도적 설계로 기술됐는지 먼저 확인한다.
  → 의도적 설계 확인됨 + 실증 문제 없음 → 이슈 목록에서 제외한다
  → 의도적 설계 확인됨 + 실증 문제 있음 → "설계 결함"으로 이슈 목록에 포함한다
  → 의도 불명확                          → 이슈 목록에 포함한다 (Phase 2에서 검증)

발굴 결과: 이슈 후보 목록 (ID, 유형, 주장, 코드위치)

Phase 2: 거짓양성 검토
────────────────────────────────────────────────────────────────────────────────

Phase 1에서 발굴한 이슈 후보 각각에 대해
D:\Main\Study\VSCode\DocChatRAG\거짓양성 검토 프롬프트.txt 의 R1·R2·R3·판관 구조를 적용한다.

실행 방법:
  - 이슈 후보 목록을 거짓양성 검토 프롬프트.txt의 안건 목록으로 변환한다
  - R1·R2·R3 에이전트를 모든 안건에 대해 병렬 실행한다
  - 판관 에이전트로 각 안건의 최종 판정을 내린다

판정별 처리:
  TRUE_POSITIVE      → Phase 3 개선 방향 제시 대상
  FALSE_POSITIVE     → 이슈 목록에서 제거 (거짓양성)
  PARTIAL            → 사용자에게 추가 정보 요청 또는 보류
  🔶사용자확인        → Phase 3에서 "사용자확인 필요" 항목으로 분류

────────────────────────────────────────────────────────────────────────────────
Phase 3: 개선 방향 제시
────────────────────────────────────────────────────────────────────────────────

Phase 2에서 TRUE_POSITIVE로 확정된 이슈에 대해서만 개선 방향을 제시한다.
FALSE_POSITIVE 이슈는 언급하지 않는다.

이슈 유형별 처리 규칙:

  [버그 ⚠️]
    - 수정 방향을 구체적으로 제시한다 (파일:라인 포함)
    - 부작용 위험이 없으면 "즉시 수정 가능" 표시
    - 부작용 우려가 있으면 "협의 필요" 표시

  [설계 🏗️]
    - 현재 구조의 실질적 문제점을 1-2문장으로 기술한다
    - 개선 방향은 방향만 제시한다 (상세 구현 금지)
    - 대규모 변경이 필요하면 "장기 과제" 표시
    - 실질적 버그·기능 결함이 없는 순수 설계 의견이면 "보류" 표시

  [성능 💡]
    - 병목 위치와 예상 개선 효과를 구체적으로 기술한다
    - 코드 로직 개선(알고리즘 변경 등)은 수정 방향 제시 가능
    - 숫자 상수·설정값은 아래 🔶 규칙 적용

  [🔶사용자확인 — 숫자 상수·설정값]
    절대 "수정 권고"를 출력하지 않는다.
    아래 형식만 출력한다:
      🔶 {파라미터명}: {현재값}
      분석: {이 값이 이론적으로 문제가 될 수 있는 이유}
      확인 필요: {사용자가 판단해야 하는 사항 — 환경·실측·제약 조건}
      ※ 실제 변경 여부와 값은 사용자가 환경 컨텍스트를 바탕으로 결정한다

  [문서 불일치 📝]
    - 소스 코드의 실제 동작과 주석·스펙 MD의 기술이 다른 경우
    - 코드가 옳고 문서가 구버전이면 → 문서 수정 방향 제시
    - 문서가 옳고 코드가 버그이면 → 코드 수정 방향 제시 (버그 유형으로 재분류)
