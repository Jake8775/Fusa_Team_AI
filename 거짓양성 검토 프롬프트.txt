대화 중 N개의 이슈·개선안이 나왔을 때 거짓양성 여부를 검토하는 용도.

[명령 형식]
  "거짓양성 검토 프롬프트.txt 기준으로 아래 N개 안건을 검토해줘.

   [안건 A] 주장: {주장 내용} / 코드위치: {파일:라인}
   [안건 B] 주장: {주장 내용} / 코드위치: {파일:라인}
   ..."

[안건별 필수 정보]
  - 안건 ID: 식별자 (예: D3-C, 이슈1 등 임의)
  - 주장: 문제라고 주장하는 내용 (1~2문장)
  - 코드위치: 파일명:라인 (예: processor.py:283)

[안건 수별 권장]
  1~15개: 한 번에 요청 (2-wave 병렬 실행)
  15개 초과: 그룹으로 나눠 요청

1. 사용자가 제시한 안건 목록에서 {ID}, {주장}, {코드위치}를 추출한다.

2. Wave 1 — 리뷰어 전체 병렬 실행:
   모든 안건의 R1·R2·R3 에이전트를 한 번에 동시에 실행한다.
   (N개 안건 × 3 역할 = 3N개 Explore 에이전트 병렬)
   각 에이전트는 자신의 역할과 안건 내용만 받는다.
   다른 안건·다른 역할의 결과를 절대 참조하지 않는다.

3. Wave 2 — 판관 전체 병렬 실행:
   Wave 1 결과 수신 후, N개 판관 에이전트를 한 번에 동시에 실행한다.
   각 판관은 자신의 안건 ID에 해당하는 R1·R2·R3 결과만 받는다.
   다른 안건의 결과는 전달하지 않는다.

4. 최종 보고:
   모든 안건의 판관 결과를 표로 정리해 보고한다.

────────────────────────────────────────────────────────────────────────────────
R1 — 코드 사실 확인 전담
────────────────────────────────────────────────────────────────────────────────
역할: 코드 사실만 확인한다. 수정 방향 제시 금지. R2·R3 결과 참조 금지.

작업:
  1. {파일:라인}을 직접 읽어 주장이 코드 사실과 일치하는지 확인한다
  2. 이 동작이 실제로 발생하는 재현 경로를 추적한다
     (호출 스택 → 실행 조건 → 분기 로직 순으로 추적)
  3. 주장에서 언급된 동작이 코드에 실제로 존재하는지 확인한다

출력:
  [R1] CONFIRMED/REFUTED/PARTIAL: 근거 1-2문장 (코드 인용 필수)

────────────────────────────────────────────────────────────────────────────────
R2 — 거짓양성 탐색 전담
────────────────────────────────────────────────────────────────────────────────
역할: "왜 이것이 실제 문제가 아닌가"를 능동적으로 찾는다.
      R1·R3 결과 참조 금지.

작업 (순서대로 확인):
  1. 호출부·UI 잠금·초기화부에 이 문제를 방지하는 가드 코드가 있는가?
  2. 다른 메커니즘이 이미 이 문제를 보완하는가?
  3. 성능 수치라면: 이론적 worst-case만 주장하는가? 실측 근거가 코드/로그에 있는가?
  4. 경쟁 조건이라면: 두 경로가 실제로 동시에 활성화될 수 있는가?
  5. 단일 파일만 읽지 않았는가? 교차 파일 컨텍스트까지 확인한다

출력:
  [R2] CONFIRMED/REFUTED/PARTIAL: 근거 1-2문장

────────────────────────────────────────────────────────────────────────────────
R3 — 의도적 결정 증거 탐색 전담
────────────────────────────────────────────────────────────────────────────────
역할: "이 코드·값이 의도적으로 결정됐다는 증거"를 찾는다.
      수정 방향 제시 금지. R1·R2 결과 참조 금지.

작업:
  1. D:\Main\Study\VSCode\DocChatRAG\스펙문서\00_카테고리_전체목록.md 를 읽어
     이 코드 컴포넌트·패턴을 다루는 스펙 MD 파일을 특정하고 직접 읽는다.
     질문: "이 구현 방식·값이 설계 의도로 기술됐는가?"

  2. 해당 소스 파일·config 파일의 주석에서 의도 명시 여부를 확인한다.

  3. 의도가 확인됐다면, 실증 증거를 추가 탐색한다:
     실제 문제가 발생했다는 증거(오류 로그, 재현 가능한 버그, 측정된 성능 저하)가
     코드·로그·주석에 존재하는가?

     판정 기준:
       의도 있음 + 실증 증거 없음 → REFUTED   (의도적 결정, 보고 불필요)
       의도 있음 + 실증 증거 있음 → CONFIRMED (의도했으나 실제 문제 발생 = 설계 결함)
       의도 없음                  → PARTIAL   (의도 불명확, 추가 판단 필요)

출력:
  [R3] 의도 확인: 있음/없음 — {근거: 스펙 MD 파일명 또는 주석 위치}
  [R3] 실증 증거: 있음/없음 — {근거}
  [R3] 판정: CONFIRMED/REFUTED/PARTIAL

────────────────────────────────────────────────────────────────────────────────
판관 — R1·R2·R3 종합 최종 판정
────────────────────────────────────────────────────────────────────────────────
역할: 해당 안건의 R1·R2·R3 결과만 참조한다. 다른 안건 결과 참조 금지.

수행 순서:

  1. R1·R2·R3 각각의 판정과 근거를 읽는다.

  2. 논거의 강도를 평가한다 (개수가 아닌 논리 강도 기준).

  3. 만장일치 점검 (R1·R2·R3가 모두 같은 방향이면):
     - R3가 스펙문서를 실제로 읽었는가? 미확인이면 판관이 직접 확인한다.
     - 세 리뷰어가 동일한 소스 파일만 읽지 않았는가?
     - 공통으로 놓쳤을 맹점을 판관이 직접 탐색한다.

  4. 숫자 상수·설정값 변경 권고가 있다면 R3 결과를 최우선 적용:
     - 의도 확인됨 + 실증 증거 없음 → FALSE_POSITIVE
     - 의도 확인됨 + 실증 증거 있음 → TRUE_POSITIVE (설계 결함)
     - 의도 불명확                  → 🔶사용자확인
       (코드 로직만으로 최적값 판단 불가, 환경·실측 기반 사용자 결정 필요)

  5. 설계 의도가 확인됐어도 실증 문제 증거가 있으면 TRUE_POSITIVE로 판정한다.
     (의도적 결정 = 면죄부 아님. 실제 문제가 있으면 설계 결함으로 분류.)

출력:
  ┌─────────────────────────────────────────────────────┐
  │ [안건 {ID}]                                         │
  │ [판정]    TRUE_POSITIVE / FALSE_POSITIVE /           │
  │           PARTIAL / 🔶사용자확인                     │
  │ [신뢰도]  HIGH / MEDIUM / LOW                        │
  │ [근거]    결정적 판정 이유 2-3문장                    │
  │ [진행방향] 수정필요 / 수정불필요 /                   │
  │            사용자확인필요 / 주석보강 / 협의필요        │
  └─────────────────────────────────────────────────────┘
